# ADR-002：用图编排（LangGraph）而不是线性链

## 状态
已采纳（2026-11）

## 背景与约束
- 流程有分支：验证通过 → 出报告；验证失败 → 回到分析补一个用例
- 需要人工中断点（高风险修复建议要人确认）
- 单人维护，不想引入平台级编排引擎

## 选项
A. 线性链（prompt chain）：A 的输出直接喂 B
B. 图编排（LangGraph）：显式状态 + 条件边
C. 引入 Airflow / Temporal 这类 DAG 引擎

## 决策
选 B。判据：需要**回退**和**中断**，线性链表达不了；DAG 引擎对单人项目过重。

## 后果
- 正面：状态显式，可回放；条件边让"验证失败重试"变成配置而不是 if-else
- 负面：图的调试比链难；状态 schema 变更要同步改所有节点
- 缓解：状态用 Pydantic 模型定义，节点签名强约束

## 如果重来
会先画图再写码（现在改过两次图，每次都要动三个节点）。

## 实现状态（2026-11-11）

实际落地与上面描述有三处偏差，如实记录：

| 项 | 决策时写的 | 实际做的 | 原因 |
|---|---|---|---|
| 状态定义 | Pydantic 模型 | `TypedDict`（`total=False`） | LangGraph 原生支持 TypedDict，节点只回传增量字段更省事；Pydantic 在这里只带来序列化开销 |
| 条件边 | 一条（验证失败回退到分析） | **两条**：无发现直出报告、验证出错有界重试 | 实现时发现"回退到分析"对同一份代码没有意义——文件没变，重扫结果一样 |
| 人工中断点 | 计划用 `interrupt` | **未实现** | 第一版只做只读扫描，"高风险操作要人确认"还没有真实场景 |

另外两条实际约束也记一下：

- **节点是纯函数**（只依赖 `state / settings / registry`），所以 6 个节点测试不需要装 langgraph 就能跑——这是刻意的，为了让核心逻辑永远可测；
- 图测试单独隔离在 `test_graph.py`，未装 langgraph 时自动跳过，不会让 CI 变红。
