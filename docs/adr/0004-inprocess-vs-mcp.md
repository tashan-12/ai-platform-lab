# ADR-004：工具通道——进程内调用与 MCP 并存

## 状态
已采纳（2026-11-11）

## 背景
ADR-001 说"工具通过 MCP 暴露"，但实际代码里有两类消费者：

- `graph-agent`：和 `mcp-server` 同一台机器、同一个 Python 进程树，需要每个请求调 10 次以上工具；
- 外部客户端（Claude Desktop / Cursor）：不在同一进程，只认 MCP 协议。

如果只有 MCP 一条通道，`graph-agent` 每次调工具都要经过 stdio 序列化 + 子进程 IPC。实测单次调用开销在毫秒到十几毫秒量级，一个报告要几十次调用，累计就是几百毫秒——而这部分开销**对结论没有任何贡献**。

如果只有进程内一条通道，外部客户端就接不进来。

## 选项
A. 只有 MCP：内部也走协议
B. 只有进程内：放弃外部客户端
C. **双通道**：`registry.py` 定义工具，`server.py` 是 MCP 适配器，`graph-agent` 直连 registry

## 决策
**选 C。** 判据是"工具的定义"与"工具的暴露方式"必须解耦：

```text
            registry.py（唯一定义源）
             │           │           │
        server.py    graph-agent   （未来）HTTP
         MCP stdio    进程内直连      适配器
```

三条硬约束支撑这个决定：

1. **签名一致性**：`server.py` 的 MCP 工具签名必须与 registry 的参数一致，否则两边会漂移。有测试盯着（`test_mcp_signature_matches_registry`），对不上立刻红。
2. **错误语义一致**：两条通道都返回同一种结构 `{ok, error, message}`，模型侧不需要区分自己走的是哪条路。
3. **安全策略只有一份**：路径收敛、命令白名单、输出截断都在 registry 下游，两条通道共用——不会出现"MCP 这边拦了、进程内那边没拦"。

## 后果
- 正面：内部调用零协议开销；外部客户端照样能接；换 SDK 版本只动 `server.py`
- 负面：**多了一个"看起来重复"的层**，新人第一反应是"为什么不直接用 MCP"
- 负面：两条通道的进程隔离不同——MCP 那条能隔离崩溃，进程内那条崩了会带走 agent
- 缓解：在 README 顶部写明这个结构的原因；用签名一致性测试兜住漂移风险

## 什么时候应该反过来（收敛到 MCP）
出现任意一条，就该把 `graph-agent` 也改成走 MCP：

1. 工具需要**独立扩缩容**（比如跑测试要吃满 CPU，不想拖累 agent 进程）；
2. 工具要用**别的语言**实现（Go / Rust）；
3. 需要**多租户隔离**——不同用户的任务不能共享同一个进程；
4. 工具稳定性差，崩一次会带走整个 agent。

现在的场景是"单机、单用户、本地开发"，四条都不满足，所以进程内是对的。

## 实现状态（2026-11-11）
- `registry.py`：`ToolSpec` + `Param` + `call/call_json/openai_tools`；
- `server.py`：60 行，只做协议接线，错误包装已全部下沉到 registry；
- 测试：registry 8 个 + 签名一致性 1 个；
- 与 ADR-001 的关系：**不冲突**——ADR-001 决定"对外用 MCP"，ADR-004 决定"对内可以不走 MCP"，两者是分层关系，不是替代关系。
