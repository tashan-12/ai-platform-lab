# ADR-005：检索采用「结构切分 + 混合打分 + 零依赖向量」

## 状态
已采纳（2026-11-11）

## 背景与约束
- 语料是工程文档（Markdown、JSON），术语密集、句式短，不是自然语言长文；
- 仓库要"clone 下来就能跑"，不能要求先下载模型或配置 API Key；
- 单人维护，检索效果必须**可解释**——出错时能一眼看出是切分问题还是打分问题；
- 需要能评测：没有数字的检索优化等于没做。

## 选项

| 维度 | 选项 A | 选项 B | 选项 C |
|---|---|---|---|
| 切分 | 固定窗口 | 按 Markdown 标题结构 | 语义切分（模型） |
| 向量 | 不用，纯 BM25 | 特征哈希（零依赖） | 真 embedding（模型/API） |
| 融合 | 单路 | BM25 + 向量加权 | 学习排序（LTR） |

## 决策
**切分选 B，向量选 B，融合走加权，再加一层轻量重排。**

三条理由：

1. **结构切分**：工程文档的语义边界就是标题。固定窗口会把一个 ADR 的"决策"和"后果"劈开，检索出的片段两头不靠。代码块更特殊——被切断的代码比不检索更糟，所以含围栏的块整块保留。
2. **特征哈希**：真 embedding 要 100–400MB 模型或外网 API，会让"零依赖"失效。哈希向量是词袋的降维投影，余弦≈词面重叠，**对精确术语（ADR-004、ToolRegistry）反而不输**；它的短板是同义改写，这一点在 README 里如实写明，不吹成"语义检索"。
3. **混合 + 重排**：单靠 BM25 对"说法不同但意思一样"的问题无解；单靠向量会丢精确匹配。0.5 加权后加"查询词覆盖率 + 标题命中"重排，把长尾召回拉起来。

## 后果（有实测数据，不是推测）

| 配置 | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|---|
| BM25 | **85%** | 90% | 95% | **0.892** |
| 纯向量 | 75% | 85% | 100% | 0.838 |
| 混合 | 80% | 95% | 100% | 0.879 |
| **混合 + 重排** | 80% | **100%** | 100% | 0.883 |

三条必须承认的事：

1. **Recall@3 提升 10 个百分点，但 Recall@1 掉了 5 个百分点** —— 重排把长尾推进前三，也让少数原本第一的答案掉到第二；
2. **MRR 反而略低于纯 BM25**（0.883 vs 0.892）—— 如果只需要"一条精确答案"，纯 BM25 更合适；
3. **评测集只有 20 条、作者自标注** —— 存在措辞偏差，绝对数值不可外推，只能用于**同一语料内的相对比较**。

## 什么时候该换真 embedding
出现任意一条：

1. 用户提问与文档措辞差异大（口语化、跨语言）；
2. 语料从"项目文档"扩到"业务知识库/工单"，同义表达多；
3. 评测集扩到 100+ 条且由**非作者**标注。

届时只换 `embedder.py`（接口已隔离），切分与检索逻辑不动。

## 实现状态（2026-11-11）
- 切分：`rag/src/ai_lab_rag/chunker.py`（标题栈 + 围栏感知 + 短块合并 + 超长硬切）
- 索引：`index.py`（SHA-1 增量；只存文档哈希与块文本，派生数据加载时重算）
- 检索：`retriever.py`（BM25 + 余弦加权 + 覆盖率/标题重排）
- 评测：`eval/run_eval.py` + `eval/dataset.jsonl`，报告见 `docs/eval-report.md`
- 测试：27 个单元用例覆盖切分/增量/检索/加载
