# rag

面向**真实工程文档**的检索：结构感知切分 → 增量索引 → BM25/向量混合 → 覆盖率重排。

```text
  语料（Markdown / JSON）
        │  loader：后缀/目录/体积过滤 + 内容哈希
        ▼
  ┌──────────┐   标题层级切块，代码块不切断
  │ chunker  │
  └────┬─────┘
       ▼
  ┌──────────┐   哈希未变 → 复用旧块；变更 → 重切
  │  index   │   只存文档哈希与块文本，派生数据加载时重算
  └────┬─────┘
       ▼
  ┌──────────┐   BM25 + 余弦加权 → 覆盖率 + 标题命中重排
  │retriever │
  └────┬─────┘
       ▼
    query / graph-agent 的 retrieve 节点
```

## 快速开始

```bash
cd rag
pip install -e .

# 建索引（对仓库根文档）
python -m ai_lab_rag.cli index --corpus ..

# 查询
python -m ai_lab_rag.cli query "工具为什么要走进程内" --corpus .. -k 5

# 看统计
python -m ai_lab_rag.cli stats --corpus ..
```

实测（本仓库 11 篇文档）：

```text
[全量] 文档 11（重建 11 / 复用 0 / 移除 0）
块数：78，平均块长 78 字符，词表 2919
索引文件：47.8 KB
```

## 三个设计取舍

**1. 结构感知切分，不是固定窗口**
工程文档的语义边界就是标题。按 800 字硬切会把"一个 ADR 的决策段"劈成两半，两头都不像。
代码块更特殊——被切断的代码片段比不检索还糟，所以**含围栏的块整块保留**，只有超过 4 倍上限才按围栏边界拆。

**2. 增量索引，不是每次全量重建**
按文件内容 SHA-1 判断：未变则复用旧块，变更则重切，删除则移除。
索引文件只存"文档哈希 + 块文本"，词频/倒排/向量在加载时**确定性重算**——
存下来只会让索引胖十倍，还容易和文本不一致。

**3. 混合检索，不是纯向量**
这一条要说清楚，因为它反直觉：

- 哈希向量**不是语义向量**。它是把词频哈希进 512 维，余弦相似度≈词面重叠；
- 对工程文档，"ADR-004""ToolRegistry"这类**精确术语**，BM25 明显强于向量；
- 所以默认 `alpha=0.5` 混合，再用"查询词覆盖率 + 标题命中"重排。

**不做真 embedding 的原因**：那要下载 100–400MB 模型或调外部 API，会让"clone 下来就能跑"失效。
升级路径写在 [ADR-005](../docs/adr/0005-rag-design.md)。

## 调参

| 参数 | 默认 | 说明 |
|---|---|---|
| `max_chars` | 800 | 单块上限（字符） |
| `min_chars` | 60 | 过短块并入上一条 |
| `hybrid_alpha` | 0.5 | 0=纯 BM25，1=纯向量 |
| `rerank_pool` | 20 | 进入重排的候选数 |
| `max_file_bytes` | 512KB | 超大文件跳过 |

## 一句实测结论

在这份语料（13 篇文档 / 97 块）上，**混合检索优于纯 BM25（Recall@3 90% → 95%）**，
但 **重排没有收益**（Recall@1 反而 -5pp），所以接口保留 `rerank` 开关、默认不启用。
完整数据见 [docs/eval-report.md](../docs/eval-report.md)。

```bash
python -m unittest discover -s tests -v
```

27 个用例：分词、切分（含代码块不切断、超长硬切、短块合并）、增量索引（复用/重建/删除/持久化往返）、检索（精确术语、标题加权、重排覆盖率）。

## 已知边界

- 词表不含同义词扩展，同义改写召回差——这是"零依赖"的代价；
- 纯 Python 全量余弦，几千块以内没问题，上万块需要换 ANN；
- 只支持 UTF-8（非 UTF-8 会替换解码并记录警告）。
